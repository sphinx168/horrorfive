# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-player prototype of a browser-based horror narrative game called **五樓 (Fifth Floor)**. The player logs in as 陳思妤 (Chen Siyu) and browses a simulated "old internet" — a nostalgic web forum, a Yahoo Messenger chat archive, a Yahoo Mail inbox, and a personal blog — piecing together a decade-old story of workplace harassment and the one person who tried to stop it. Everything happening *today* instead plays out in a present-day group chat (茶水間) — which is deliberately *not* part of that browser: it is a separate chat app layered over it (fullscreen on a phone, a docked window on a desktop), because nobody reads their group chat in a browser tab. The game shuttles between the two apps. There is no build system, no dependencies, and no test suite: the entire game is one self-contained HTML file.

- [五樓_單人版.html](五樓_單人版.html) — the whole game: markup, CSS, and vanilla JS in one file, no external resources.
- [恐怖留言板遊戲_idea.md](恐怖留言板遊戲_idea.md) — the design document (Traditional Chinese), **single-player only**. This is the source of narrative truth: character backstories, the intended emotional arc (contempt → doubt → grief → guilt), the linear-disclosure-chain puzzle design (§四), the flow-to-`prog`/`GATES` mapping (§六), the decisions already locked into code (§七 設計定案), and the remaining open items (§八 待決定 — currently only the second pass over 序章／第一章 text). Read this before making any narrative or pacing change — code changes should stay consistent with it, and if a design question it flags as undecided gets resolved in code, tick it off and reflect the decision back into the doc.
- [index.html](index.html) — a meta-refresh redirect shim to `五樓_單人版.html` (for hosts that serve `index.html` by default, e.g. GitHub Pages). Not game logic; update its URL-encoded href if the main file is ever renamed.
- [archive/恐怖留言板遊戲_idea_多人協力版原始設計.md](archive/恐怖留言板遊戲_idea_多人協力版原始設計.md) — **archived, not maintained.** The original 4-player co-op design (shared-nothing screens, voice coordination, password/cross-reference/relay gates, the four-anomaly-puzzle mechanic). The project's target is now the single-player build; this file is kept only in case a multiplayer version is revisited later. Do not treat it as current design guidance.

## Running it

No server, no build. Just open the file directly:

```bash
start "" "五樓_單人版.html"
```

(or double-click it / open via `file://` in a browser). Login is pre-filled (`siyu_1120` / `1120`) since it's single-player and the "account" is fixed to one character.

## Architecture (五樓_單人版.html)

The file simulates a **tabbed browser inside the page** — a fake browser chrome (`#browser`, tabstrip, omnibox) rendered around an inner `#viewport` that swaps between different "site" skins. The shell is a full-height (`100dvh`) flex column: `.tabstrip` and `.omni` are `flex:none` and never move, and `.viewport` is the only scroll container (`flex:1;overflow-y:auto`) — so scrolling a page leaves the browser chrome in place, exactly like a real browser. Consequences for JS: `#browser` is shown with `display:flex` (not `block`), "scroll back to the top on navigation" is `toTop()` (which resets `viewport.scrollTop`, not `window`), and anything measuring scroll position — `markBlogRead()`'s scrolled-to-the-bottom check, and its `scroll` listener — reads `#viewport`, not `window`. Everything is driven by one global progress counter and a handful of data tables at the top of the `<script>` block; there is no framework, no router, no external state.

**Core data model, all declared as plain JS arrays/objects near the top of the script:**

- `ME` / `USERS` / `who()` — the player's identity and the account→given-name map for the six colleagues. The board speaks in account ids but the characters call each other by name, so both are rendered together and the player never has to keep a mental lookup table.
- `CHAT` / `AVATARS` — the present-day group chat, which carries the entire "today" storyline. `CHAT` is an ordered list of scenes; each has a `when()` predicate (`prog>=N`, `seen.has(docId)`, `mailRead.has(mailId)`, …) and a list of `steps`. A step is one of: `{u,c}` a message from someone (typing animation first; her own messages skip it), `{u,c,now}` shown instantly with no animation (the opening small talk), `{me}` a dashed draft bubble that pauses playback until the player clicks it to "send", `{me,end}` the final line that fires `prog=6`, `{u,share}` a clickable link card pointing at a `DOCS` id, `{u,url,lbl}` a bare URL (the opening 五樓 link, which enters the login page), and `{sys}` a centered system/silence line. `AVATARS` gives each speaker a CSS-drawn circular avatar (surname + color), no image assets.
- `DOCS` — every readable document in the game (forum threads, the messenger archive, the mail inbox, the blog). Each entry has an `id`, a `skin` (which renderer draws it: `wulou`/`archive`/`inbox`/`blog`), a `site` label, and an `at` (the minimum `prog` value at which it unlocks). Forum entries also carry `idx` (the board-homepage row: floor count, last replier, display time, a view count `hits`, and a `ts` sort key from `TS()`/`TS_NOW()`), optionally `top` (pinned — `t_rules`, the 2015 board rules, is the only one; it sorts above everything and repeats on every page) and optionally `peek`/`lockTitle` (locked-state teaser text — only consumed by the currently disabled 我的最愛 tab, see below). Individual `posts` inside a thread can carry their own `at` (drip-fed replies) or an `rid` (a deleted floor and its restored counterpart — see `restored`).
- `BOARD_DECO` + `boardRows()` — the board homepage (`board_index`) is generated, not authored: unlocked `wulou` docs are merged with a handful of un-clickable decorative threads and sorted by `ts` (pinned `top` rows first), so the board looks like it has been alive for eleven years and new threads surface at the top. `renderBoardIndex` pages the non-pinned rows `PER_PAGE` at a time (`boardPage`), and both it and `renderThread` are wrapped in the free-host furniture — `wlAd()` (the ad banner a free host injects at the top of every page; `adOpen` closes it for the session) and `wlFoot()` (visitor counter, thread count, last-updated date, Powered by). The counts in the footer are derived from `boardRows()`, so they can never contradict what is on screen.
- `GATES` — the four puzzle steps that advance the chapters, in order: `g_mail` (Yahoo Mail login), `g_ytl` (the board's admin login, as 林昱庭), `g_admin` (restoring the deleted floor), `g_search` (searching his name). Each gate has a `skin` (`yahoo`/`admin`/`restore`/`search`) that picks its renderer, plus `ch`/`label`/`need` copy for the checklist (currently unreachable — the only renderer for it is the disabled 我的最愛 tab). An optional `needChat` names a `CHAT` scene that must have finished playing before the gate's tab is allowed into the tabstrip, so a gate can't appear on screen before the story has motivated it (`g_mail` waits for `c_intro`). Most define `fields` with an `answer` list checked via fuzzy `match()`/`norm()` (handles full-width/half-width punctuation, spacing, case — a typo-tolerance holdover from the original co-op design, kept here purely to forgive input mistakes), optional `forgot` hint and `nudge` per-wrong-answer messages. `g_admin` is the exception: no fields, it's a click-to-restore list driven by `restorables()`.
- `AFTER` — what happens once a gate is solved: `unlockAt` (the new `prog` value) and `said` (a full-screen narration beat played before the next page, via `saidNow`/`renderSaid`).
- `SITE` — per-doc/per-gate metadata for the fake browser chrome: tab label, fake URL, favicon color.

**Chat engine:** `chatCheck()` scans `CHAT` and appends the steps of every scene whose `when()` now holds (each scene fires once, tracked in `chatFired`; `chatDone` records the ones that finished playing). It is called at the end of `render()`, so any state change re-evaluates the triggers. When a scene finishes (`chatNext` reaches its `_done` marker) it calls `render()` rather than just `chatCheck()`, because `syncTabs` may now have a `needChat` gate tab to add. Playback (`chatPump`/`chatNext`) only runs while the chat app is actually open (`chatHere()` = `chatOpen && !saidNow && prog<6`) — otherwise the steps sit in `chatQueue`, the dock bubble shows an unread count (`chatPending()`, which stops counting at the next draft bubble so it can't leak how much is coming, and reports 1 while a draft bubble is still waiting to be clicked) and a push banner (`showToast()`) drops in from the top of the screen. Clicking a draft bubble calls `chatSend()`.

**Chat app shell:** there is exactly one chat node for the whole game — `#chatapp`, a `position:fixed` layer *outside* `#browser` (fullscreen under 600px, a docked window bottom-right above it), holding the message list `#plMsgs` and the input bar `#plIn` that doubles as the "click the draft bubble" hint (`chatPaint()` / `chatRows()` / `chatInBar()`). The conversation is therefore literally continuous across the login boundary: the pre-login screen is that same app carrying the `solo` class (centered like a phone, back button hidden), and nothing is ever moved or re-created. `openChat()`/`closeChat()` flip `chatOpen` and hand off to `syncApp()`, which owns the app's `on`/`solo` classes plus `#chatdock`'s visibility and badge — call `syncApp()` **before** `chatPaint()`, since a hidden element has no scroll height and the scroll-to-latest would land on nothing. Tapping a `share` card or the opening URL card calls `closeChat()` first: that link is being opened over in the other app. Consecutive messages from the same speaker are grouped (`cont` class hides the repeated name and avatar), and `.pl-stack` uses `margin-top:auto` so messages sit on the bottom edge.

**Progress state:** a single `let prog` gates almost everything — which `DOCS` and posts are visible, which gate is active (`curGate()` maps `prog` ranges to a gate), and when the ending fires. It advances only at fixed points: gates set `prog = AFTER[id].unlockAt` (→1, 2, 3), clicking the search result sets `prog = 5` and opens the blog, and sending the final chat draft sets `prog = 6` → `renderEnd`. (4 is currently never assigned; `curGate()` still accepts it.) Other mutable state: `loggedIn`, `chatOpen` (is the 茶水間 app open — starts `true`, since the game opens inside the conversation), `boardTab`, `seen` (which docs have been opened — also drives chat triggers), `mailRead` (which mails have been opened — same), `blogRead` (set by `markBlogRead()` once the blog is actually scrolled to the bottom; the ending scene waits on it), `restored` (floors recovered in the admin backend), `mailFolder`/`mailOpen`, `gateDone`, `MAX_DOC_TABS` (3; opening a fourth document tab closes the oldest), and `NOTES_TAB_ENABLED` (false — the 我的最愛 tab is hidden because it broke the immersion, and its "collected docs" function is now served by the chat's `share` link cards; `notesContent()`/`renderNotes()` are kept behind the flag). There is no persistence: reloading restarts the game.

**Rendering:** `render()` → `syncTabs()` (keeps the open tab list consistent with the current `prog`; the board tab is first and can't be closed) → `renderChrome()` (tabstrip/omnibox) + `renderPage()`, then `syncApp()` and `chatCheck()`. The chat is not part of `renderPage()`'s dispatch at all — it is an overlay repainted only by `chatPaint()`. `renderPage()` shows a pending `saidNow` beat first, then dispatches on the active doc's `skin` or the active gate to `renderBoardIndex`, `renderThread`, `renderArchive`, `renderInbox`, `renderBlog`, `renderGate`, `renderRestore`, `renderNotes`, or `renderEnd`. Each renderer does a full `innerHTML` re-render (no diffing) and re-binds its own handlers.

**Debug panel:** `#dev` exists only when the URL carries the `#dev` hash (`…/五樓_單人版.html#dev`; `index.html` forwards the hash). `DEV_STAGES` lists the jump targets — each entry rebuilds state directly (`prog`, `done` gates, `at` tab/doc, `chat:1` for the stages that should land with the 茶水間 app open), and `devApply()` backfills every already-triggered `CHAT` scene into `chatShown` before `render()` + `chatPaint()`. The panel wraps `render`/`openChat`/`closeChat` to keep its status line live, so bind UI handlers to those through an arrow (`()=>closeChat()`) rather than by reference, or the binding freezes on the un-wrapped version. `devFast` (the 秒播 switch) collapses every chat delay via `dly()`.

**When adding new story content:** anything happening *today* belongs in `CHAT`, not on the board — the forum is a dead archive and nobody posts there any more (the annual 〈又到了〉 ritual survives as a `filler:1` thread: openable, but it reads as a dead-end on purpose; `BOARD_DECO` is empty and kept only as a hook for genuinely un-clickable rows). For a document, add a `DOCS` entry (pick a `skin`, write `posts`/`days`/`mails`/`entries` in that skin's shape), give forum threads an `idx` so they appear on the board homepage, and register it in `SITE`; if it should be gated behind a puzzle, add a `GATES` entry and an `AFTER` unlock mapping, and give the new `prog` value a `CHAT` scene so the group reacts to it. Keep new copy in Traditional Chinese matching the existing character voices (see the design doc's per-character dialogue notes). The `add-story` skill (`.claude/skills/add-story/`) carries this whole procedure in full — the legal `at` values, the per-skin field templates, and the six checks the guardrail enforces — so invoke it rather than reconstructing the shapes from scratch.

**Guardrail:** `.claude/hooks/check-five-floor.mjs` runs on every write to the HTML file and rejects obviously broken data — self-containment (no external resources), `DOCS`↔`SITE`↔`GATES`↔`AFTER` cross-references, unreachable `at` values, orphaned restore ids, duplicate board sort keys, `CHAT` scenes pointing at non-existent docs or speakers, a missing `end:1`, and any `prog` step with no chat reaction. If the file's structure is ever refactored, update the hook's slicing to match.

**Authoring tooling:** writing story text is the most frequent kind of change here, so it has its own support in `.claude/`:

- `skills/add-story/` — the procedure for adding or rewriting any story text. `SKILL.md` is the workflow (which layer the content belongs to, the six landing checks, the hard rules); `references/skins.md` is the copy-paste field reference for all five data shapes plus `GATES`/`AFTER`.
- `agents/voice-check.md` — per-character voice proofing. Carries the measured punctuation fingerprints (宗翰 ~61% full stops, 文豪 ~70%, 冠廷/雅琳/思妤 0%) and, most importantly, the 阿哲≡2015-思妤 typing match that the whole reveal rests on. Run it after touching any dialogue.
- `agents/narrative-continuity.md` — dates, floor numbers, time-span arithmetic, and disclosure order. Explicitly *not* voice — that belongs to `voice-check`.
- `agents/design-doc-sync.md` — drift between the design doc and the implementation, plus §八 items that are actually settled in code by now.

All three agents are read-only: they report, they don't edit.
